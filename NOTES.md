## Enforcement and findings

The server resolves `user_id` to a role and region; neither comes from the model or a tool argument. `query_data` accepts a strict typed plan, and the trusted compiler checks **selection, predicates, grouping, metrics, ordering, lifecycle, and region** before emitting parameterized SQL. SQLite is opened read-only, with a query-only pragma, timeout, and row cap. Results pass disclosure checks before entering model context or the chart tool. The chart tool accepts only an approved result ID owned by the same user, conversation, and policy fingerprint. HTTP bearer sessions are local demo identities; the API checks ownership again when releasing a response. A role change invalidates conversation history and cached results. Tool refusals return `status`, `code`, and a reason; the model loop treats them as terminal. Empty authorized results have a different status and UI treatment.

The original trust error was treating the model as the access boundary. A polite answer cannot undo a restricted row already placed in a tool result. Other gaps found while working on the boundary include: restricted fields used as filters or sort keys; rows admitted through transaction/alert joins; soft-deleted customers; admin mistaken for a superuser; fair-lending identifiers or case notes; unsafe customer and protected-class aggregates; inference through a single suppressed cell; cross-role history and chart reuse; SQL writes; and sensitive literals copied into otherwise permitted memo or note text. The extended eval adds L18–L24 for case-note access, offboarding, shared history, reviewer purpose, empty aggregates, identity mutation, and duplicate records for one person. Direct tests also cover role changes during a request, read-only database access, parameterization, chart ownership, and generalization. For analysts, ZIP, date of birth, and annual income are generalized for **row presentation** only. Exact ZIP and income-threshold *selection* is refused, including by the narrow pre-model request guard added after L15/L16 varied between runs. The compiler remains authoritative for submitted plans.

The current design cannot guarantee that arbitrary free text never contains a restricted fact. `scrub_text` matches known sensitive values without case sensitivity before model release, including direct identifiers embedded inside other text. A temporary-database probe reproduced a wrapped national ID in a memo and a wrapped email in a case note reaching released text and chart data; the revised scrubber withheld both from model context. It still cannot recognize paraphrases, partial identifiers, newly introduced secrets, or semantic descriptions of protected traits. Full prevention requires controlled text ingestion, stronger classification/redaction, and a defined policy for quoting source text. The regex request guard likewise cannot understand every natural-language predicate. The compiler prevents forbidden field access, but an unrecognized request might be answered as a different, coarser question. In a live follow-up, the model asserted the one high-value transaction was a wire without executing a new query; that happened to be true in this fixture, but the preceding count query did not establish the channel. Follow-ups therefore still need stronger evidence checks to avoid unsupported claims. Protected-class breakdowns use one fixed company-wide active cohort, preventing the demonstrated subtraction of a filtered report from an unfiltered report. Other aggregate differencing can still occur; independent per-query floors do not provide a formal privacy budget.

## Audit record

Each turn emits one owner-only JSON line at `.runtime/audit.jsonl`, keyed by `audit_id`. It records identity (`user_id`, name, role, region), resolved scope and policy version, conversation ID, final status/denial, model usage and latency, and every executed SQL statement with bound parameters, execution row count, **released rows and count**, status, and redactions. Withheld rows are recorded as `status: withheld` with an empty `released_rows` list; internal redaction lookups are marked `internal_only`. For example, an analyst count has `c.region = ?` with `WEST`, `c.deleted_at IS NULL`, and a released count row. The browser shows the audit reference, SQL, parameters, released-row count, and redaction notes, while hiding private execution counts and internal lookups. The audit file itself is sensitive and would need encryption, retention rules, central storage, and access review outside this demo.

## Cost, latency, and scale

Across **52 model requests** in the completed expanded run (49 scored cases plus three follow-up setup turns), p50 was **2.252 s** and p95 **5.160 s** per request. Mean usage was **2,951 input tokens** (724 cached) and **89 output tokens**; estimated mean cost was **$0.01416**, total **$0.736541**. The 25 scored correctness turns alone averaged $0.016113, excluding their three setup turns, which cost another $0.056812 in total. Estimates use the locally configured rates in `agent/config.py` dated 10 October 2026, not an invoice. Zero-token deterministic denials are included. At 100× questions, serial model latency, cost, single-process in-memory sessions, and JSONL audit writes become bottlenecks. At 100× rows, SQLite scans, the 5,000-row safety cap, and the full-customer lookup used for free-text redaction become immediate limits. A real service needs durable session storage, indexed/partitioned queries, bounded aggregation, a dedicated audit sink, rate limits, and a measured privacy strategy before scaling.

## AI log and deliberate cuts

An independent coding-agent review reproduced a lowercased identifier in a transaction memo, a protected-class subtraction attack, a false income-guard denial for a transaction amount, and a denied turn showing an earlier partial result. I corrected known-value redaction to ignore case, made protected-class reports use one fixed cohort, narrowed the income guard, and discarded partial results on terminal denial. A temporary-database adversarial probe found that known direct identifiers embedded in longer strings still escaped redaction; I tightened that boundary and verified both memo and case-note paths. The first full model rerun exposed the customer-count alias mismatch in the eval harness, which I corrected without weakening the transaction count check. A later live follow-up answered a transaction-channel question without new SQL, so I added three multi-turn eval cases and a deterministic harness test that rejects a lucky numeric answer without current-turn data. The first expanded full run hit model-service errors; I did not bypass or treat them as leak failures. At the user's later request I retried after an x4 smoke test showed the service was available, and the complete expanded run passed. Actual hours spent across earlier sessions are not recoverable from this workspace, so I do not claim compliance with the 4–8 hour cap.

The visible coding-assistant prompts for the final passes were **“continue the work & finish the take home with deliverables”**, **“Finish the post-review verification and submission of this take-home”**, and a request to add follow-up tests, together with `TASK.md` and the workspace. The runtime model prompt is the `SYSTEM` constant in `agent/baseline.py`; it tells the model to use the field catalog, structured tools, UTC boundaries, currency units, and scope. I inspected the earlier saved eval, which showed L15/L16 sometimes **answered instead of declining** despite that instruction. A focused rerun passed them, confirming nondeterminism. I overrode the model with a deterministic exact-predicate check and tests. The answer policy also explicitly overrides likely model mistakes about reviewer access, compliance protected-class access, analyst generalization, and FX/age data that do not exist. The completed full run let the model choose `COUNT(DISTINCT customer_id)` for customer counts and changed only the eval interpretation of that equivalent result. Earlier coding-assistant prompts are not present in the workspace, so I have not reconstructed or claimed them.

I kept the query language finite instead of exposing arbitrary SQL, and did not add a general ORM or policy framework. I did not add external authentication, real customer data, FX conversion, fraud-decision inference, or cross-query differential privacy; each would claim a guarantee this local exercise cannot support. I kept sensitive execution rows out of the browser while retaining them in the private audit file. The demo intentionally runs as one process and one fictional warehouse.

## Interface and walkthrough

Run the commands in [README.md](README.md) and open `http://127.0.0.1:8765`. The React screen shows the selected identity and scope, suggested questions, conversational follow-ups, a clear refusal/empty distinction, formatted result cards and tables, Vega-Lite charts, and expandable query details. Switching identity starts a fresh bearer session and drops visible history; late responses from the old session are ignored. I left raw model tool JSON and private audit rows off the screen because they add noise and can contain restricted content.
